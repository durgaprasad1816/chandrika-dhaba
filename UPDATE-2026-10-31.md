# Chandrika Dhaba update — 31 October 2026

This update is based on the uploaded `chandrika-dhaba17.zip` source.

## Implemented in this update
- Manager menu editor now supports selecting multiple preparation options separately for each dish. Only selected options are sent to the waiter menu; options can be added to or removed from the shared preparation-type list.
- Order validation now rejects a preparation selection that is not enabled for that specific dish.
- Per-item waiter serving API: a waiter can mark a line served only after the kitchen marks that line Ready. The order becomes Served after all its lines are served.
- Table payment totals and generated bill lines include served items only. Unserved lines are excluded from the payable subtotal and bill line list.
- Kitchen response now separates pending rows into `oldOrders` (pending for at least 10 minutes) and `newOrders`; the manager kitchen screen renders both sections. Existing starter-first gating remains.
- Manager table list includes three additional independent bed locations (Bed 1–3), using location IDs 101–103. These locations support separate table state, waiter allocation and orders.
- Customer menu sections now have horizontal scrolling with left/right controls.
- Customer public menu payload no longer exposes waiter-only preparation controls/options.

## Bed QR URLs
Generate QR codes pointing to the same app URL used for table QR codes, replacing the table parameter with:
- `?table=101` — Bed 1
- `?table=102` — Bed 2
- `?table=103` — Bed 3

Assign a waiter to the corresponding bed from the manager table allocation screen.

## Build
Requires JDK 17 and Maven:
```bash
mvn clean package
java -jar target/chandrika-dhaba.jar
```

## Important remaining work
This is an incremental source update, not a claim that every requested UI workflow is finished. In particular, the waiter front-end still needs a complete persistent multi-table workspace with independent carts and the per-line Ready/Served controls wired into the cart popup; the customer-facing live wait-time display needs a proper per-order queue estimate refresh; and the special-dish Try This interaction should be checked against the final menu data. These items should be completed and browser-tested before live restaurant deployment.
